# Project Overview

> 最后更新：2026-07-21  
> 用途：定义《谁是大厨生》的项目身份、目标和范围。事实状态以 `Current_Status.md` 为准，设计取舍以 `Design_Pillars.md` 和 `Decision_Log.md` 为准。

## 项目身份

- 中文名：《谁是大厨生》
- 英文暂定名：Who's the Beast Chef?
- 类型：2D 俯视角、烹饪 × 战斗 × 实时构筑 × 轻度资源管理
- 引擎：Godot 4.6
- 脚本语言：GDScript
- 团队规模：两人
- 第一版目标：在 2026 年 9 月左右完成可用于游戏开发实习作品集的完整 Demo
- 长期训练目标：在 2027 年 1 月参加 Game Jam 前完成多轮完整开发训练

## 一句话概念

玩家在高压、混乱的厨房中亲自战斗，同时处理食材、持续烹饪并调整构筑，把料理转化为影响战局的战斗能力。

## 为什么做这个游戏

项目希望把“做饭”和“战斗”合并成同一个实时决策循环，而不是“完成料理后进入战斗”，也不是把烹饪做成战斗前的附属小游戏。玩家需要在有限时间、空间和资源下判断：现在应该战斗，还是先处理厨房。

名称中的双关逻辑是：中文从“大厨生”联想到“大畜生”；英文则从 **Best Chef** 联想到 **Beast Chef**，重点在 **Best / Beast 的近音双关**。它表达了玩家既可能成为最佳厨师，也可能成为制造厨房灾难的“野兽”，而不是简单把 Chef 与 Beast 当作对应翻译。

## 玩家体验目标

1. **忙乱但好笑**：压力和失误产生可理解、可复盘的欢乐结果，而不是恶意惩罚。
2. **料理即战斗**：烹饪结果直接改变防守局势，每次做菜都应有战术意义。
3. **组合有创造性**：少量食材与料理能够形成明显不同的战斗方案。
4. **资源选择有代价**：玩家不能无脑选择纯数值更高的方案，需要权衡时间、食材、位置和当前威胁。
5. **压力产生欢乐事故**：核心体验还包括“压力环境 → 混乱决策 → 欢乐事故”，而不只是“料理 → 战斗”。

多人混乱合作是项目的长期探索方向。未来可以探索玩家分工、互相影响、争抢空间与厨房连锁事故；第一版 Demo 仍可用单人模式验证核心循环，不能为了提前实现多人而牺牲完成度。

## 核心循环

```text
准备阶段：观察敌人、整理资源并形成初步构筑
        ↓
战斗开始
        ↓
玩家战斗，同时持续处理食材与烹饪
        ↓
料理形成战斗能力并调整构筑
        ↓
完成本轮复味并获得波次奖励
        ↓
下一轮准备
        ↺
```

当前 Prototype 0.4 用“首波前自由准备 → 三波战斗 → 两次波间准备”验证上述循环；这是灰盒实现，不把首波准备形式、波次数或时间固化为正式 Demo 规则。实时实现状态以 `Current_Status.md` 为准。

准备阶段不能让玩家提前完成整轮战斗资源；其目标是形成开局构筑。战斗阶段厨房保持开放，烹饪与战斗持续互相争夺玩家的时间、位置和资源。

阶段一中期的完整规则、临时方案、长期方向、未决事项和旧方案修正统一记录在 [`Stage1_Midterm_Summary.md`](./Stage1_Midterm_Summary.md)。

## 核心主题

核心表达为：“天大地大，吃饭最大。”游戏关注身体需求、规律饮食和人与食物的关系。玩家战斗的本质是帮助味真族恢复正常的味觉、身体状态与满足感，而不是单纯消灭敌人；“味能”及“复味 / 调和”等部分名称仍待最终确认。

## 参考作品及学习目标

- 《胡闹厨房》：简单动作在时间、空间和任务冲突下形成混乱；失败应具有喜剧性。
- 《鸡械绿洲》：小体量系统也能形成战斗组合与防守循环。
- 《杀戮尖塔》：资源有限时的构筑选择，不依赖单纯数值成长。

参考作品用于提炼设计原则，不直接复制其完整系统或内容规模。

## 第一版 Demo 范围

### 必须包含

- 一个可控制角色
- 一个小型、清晰的厨房 / 防守场地
- 玩家亲自参与战斗，战斗过程中厨房持续开放
- 一个轻量、有限空间的背包原型
- 少量基础食材
- 2 至 3 种有明显差异的料理
- 验证料理能够作为影响战斗局势的核心资源
- 少量敌人类型
- 一个完整、可重复运行的胜负流程
- 最低限度但清晰的操作反馈与 UI

### 明确不做

- 联机功能
- 大型肉鸽结构
- 大地图
- 复杂剧情
- 大量角色
- 完整经营系统
- 为未来可能性提前搭建的大型通用框架

### 范围解释

首版采用一个玩家角色验证核心循环。“玩家之间互相影响、互相坑害”与多人混乱合作是项目的重要长期方向，因此交互、空间和场景设计应避免无必要地封死未来扩展可能；但首版不承担多人功能的实现成本，不能为了未来多人牺牲当前 Demo 的完成度。任何多人扩展必须在单人核心循环成立之后重新立项评估。

### 料理战斗化验证范围

第一版的目标不是立即确定料理战斗化的最终实现形式，而是验证以下核心假设：

> 料理是否能够成为影响战斗局势的核心资源？

原型可以探索：

- 近战装备
- 远程装备
- 炮台
- 陷阱
- 召唤物
- 主动技能
- 范围增益
- 防御能力
- 回复能力
- 特殊规则型效果

根据试玩结果决定最终方向，不在验证前过早绑定单一场景结构、数据结构或部署架构。

## 团队分工

### 主开发者

- 游戏设计与项目统筹
- Godot 程序开发
- 系统与数值设计
- Git 版本管理
- 测试、复盘与作品集整理

### 美术队友

- 角色与场景设计
- 食材、料理素材
- UI 视觉
- 动画与特效

工程整合由主开发者负责；美术资源通过约定目录和命名交付，避免两人同时修改同一 Godot 场景。

### AI 开发协作

- GPT Codex 默认承担项目主程、架构、核心系统、复杂问题和整体方向。
- DeepSeek Codex 默认承担已明确方案的小型实现、数值、UI、快速验证和简单修复。
- 两个 AI 不依赖彼此的聊天记录；代码与 `AI_Context/` 是共享事实来源。具体读写与交接规则见 `AI_Collaboration_Guide.md`。

## Demo 成功标准

第一版成功不以“功能数量”衡量，而以以下结果衡量：

- 新玩家能理解“处理食材 → 持续烹饪 → 料理改变战斗方式”的关系。
- 2 至 3 种料理会导致可感知的战术差异。
- 玩家能够感受到烹饪结果确实改变了当前战斗局势。
- 一局中至少出现一次由压力、位置或操作失误造成的有趣混乱。
- 游戏可以从开始完整运行到胜利或失败，没有阻断流程的错误。
- 代码与场景足够清晰，能够在作品集中解释设计思路和技术实现。

## 当前待验证问题

- Prototype 0.4 的小炒远程、战斧近战和涮肉诱食陷阱中，哪些经人工试玩后值得保留、调整或淘汰？
- 涮肉陷阱的自由放置只是当前代表性实验；未来其他部署型料理采用自由放置、固定槽位还是自动部署仍未确定。
- 厨房操作需要几步才能产生“忙乱但不繁琐”的节奏？
- 第一版敌人与厨房目标之间的空间关系是什么？
- 长期多人方向采用本地合作还是其他形式？此问题不阻塞首版单人 Demo。
