# Development Rules

> 最后更新：2026-07-21  
> 用途：约束人类开发者与 AI 助手的日常开发流程、技术选择和交付标准。

## 每次开发前的上下文读取顺序

1. `AI_Handoff.md`：先读取最近一次交接、当前禁区和建议入口。
2. `Current_Status.md`：确认当前版本、运行状态和正在处理的工作。
3. `Pending_Tasks.md`：确认真正授权中的任务、已知问题和未决事项。
4. `Project_Overview.md` 与 `Design_Pillars.md`：确认项目目标、体验原则和设计红线。
5. `Decision_Log.md`：确认已正式决定、已废弃和被替代的规则。
6. `Development_Roadmap.md`：确认任务属于哪个里程碑，避免把长期方向误当成本轮范围。
7. `AI_Rules.md` 与 `Coding_Standards.md`：确认 AI 权限、代码与工程习惯。
8. `AI_Work_Log.md` 最近记录：理解另一位 AI 最近实际改了什么、测试到什么程度。
9. `Stage1_Midterm_Summary.md` 与当前相关的 Prototype / 阶段归档：读取具体设计规则、临时参数、入口和测试结果。
10. 检查实际 Godot 工程、场景、代码以及 Git 状态；文档与工程冲突时，先记录差异，不凭猜测覆盖任一方。

其中 `Current_Status.md`、`Decision_Log.md`、`Development_Roadmap.md`、`AI_Work_Log.md`、`Pending_Tasks.md` 和 `AI_Handoff.md` 是任何 AI 开始开发前的强制阅读项。

## 功能开发流程

所有重要功能遵循以下顺序：

```text
分析需求
  ↓
提出最小实现方案与替代方案
  ↓
说明涉及的 Godot 节点、场景、脚本和数据
  ↓
获得确认（当方案会影响玩法或范围时）
  ↓
编写代码 / 修改场景
  ↓
运行测试与人工验证
  ↓
更新 Current_Status.md、AI_Work_Log.md、Pending_Tasks.md 与 AI_Handoff.md
  ↓
涉及设计变化时更新 Decision_Log.md
  ↓
由项目负责人决定是否形成 Git 提交
```

不得在需求和验收标准不清楚时一次性生成大量代码。

## 范围控制

每个新功能必须回答：

1. 是否增强核心体验？
2. 是否帮助按时完成 Demo？
3. 是否值得实现、测试和美术成本？

默认策略：

- 先实现最小可验证版本，再决定是否扩展。
- 首版明确排除联机、大型肉鸽、大地图、复杂剧情、大量角色和经营系统。
- 不为“以后可能用到”提前构建通用框架。
- 同一时间只允许一个主要玩法系统处于未完成状态。

## 当前技术基线

- Godot：4.6 系列；当前编辑器为 4.6.2 stable
- 语言：GDScript
- 游戏维度：2D 俯视角
- 渲染器：Compatibility / `gl_compatibility`
- 设计分辨率：1280 × 720
- 拉伸模式：`canvas_items`
- 版本管理：Git，默认分支 `main`
- 当前项目文件：`GodotProject/project.godot`

改变以上基线前，必须在 `Decision_Log.md` 记录原因、影响和迁移方案。

## 目录与命名规则

当前顶层职责：

- `GameDesign/`：玩法文档、数值表、设计草稿和美术需求。
- `GodotProject/`：可直接由 Godot 打开的游戏工程。
- `AI_Context/`：人类和 AI 共用的长期项目上下文。

Godot 工程现有目录：

- `Assets/`：通用导入资源和美术交付。
- `Audio/`：音乐与音效。
- `Scenes/`：游戏场景。
- `Scripts/`：GDScript。
- `UI/`：UI 场景与资源。

命名约定：

- 文件和新子目录使用小写 `snake_case`，如 `player.gd`、`main.tscn`。
- Godot 节点使用 `PascalCase`，如 `Player`、`IngredientDetector`。
- GDScript 变量、函数和信号使用 `snake_case`。
- 输入动作使用语义名称，如 `move_left`、`interact`，不使用具体按键名。
- 资源文件名体现内容和用途，避免 `new_scene_2.tscn`、`script1.gd`。

随着项目增长，允许把相关场景、脚本和资源放入同一功能子目录；不要为了遵守早期空目录而制造大量跨目录依赖。结构调整必须小步进行并记录。

### 功能导向的结构原则

Godot 项目优先采用清晰、功能导向的结构。目录和依赖应帮助开发者快速找到“玩家、食材、烹饪、战斗、敌人”等实际功能，而不是展示架构技巧。

避免：

- 过度抽象
- 复杂架构
- 为未来尚不存在的需求提前设计
- 为了形式整齐而把强相关文件拆散到难以追踪的位置

代码和场景设计应该：

- 易理解
- 易修改
- 方便新人学习
- 能够用小步重构适应已经出现的真实需求

当简单方案足以验证当前玩法时，默认选择简单方案；只有重复问题已经出现并有测试依据时，才引入新的抽象层。

## Godot 场景与脚本规则

- 游戏概念优先做成可独立运行、可实例化的场景，例如玩家、食材、料理单位和敌人。
- 场景负责节点组成和可编辑参数，脚本负责行为。
- 节点只承担清晰职责，避免把全部逻辑写入 `Main`。
- 场景之间优先使用信号或明确接口通信，避免依赖脆弱的深层节点路径。
- 只有在确认存在跨场景生命周期需求时才添加 Autoload。
- 不在第一版中搭建抽象 ECS、全局服务容器或大型事件总线。
- 数值先使用可检查的导出变量；配方和单位增多后再评估自定义 Resource 数据化。
- 物理移动放在 `_physics_process()`，输入动作通过 Input Map 管理。

## 代码规则

- 代码以初学者能够解释和维护为标准，不追求炫技式抽象。
- 函数短小、命名表达意图；注释解释“为什么”，不重复代码表面含义。
- 关键依赖使用类型标注；避免无必要的全局可变状态。
- 先处理正常流程，再为真实出现的边界情况增加保护。
- 不保留已知报错、失效节点路径或未说明的临时代码。
- AI 生成的代码必须由主开发者理解，并通过实际运行验证后才能视为完成。

## 测试与完成定义

一个功能只有满足以下条件才算完成：

- Godot 工程可以无解析错误地打开。
- 相关场景可以单独运行或通过主流程运行。
- 已验证正常路径和至少一个关键失败 / 边界路径。
- Debugger 没有新增未解释错误。
- 操作结果有足够反馈，可由开发者描述验收结果。
- `Current_Status.md` 已同步。
- 重要设计或技术决定已写入 `Decision_Log.md`。
- `AI_Work_Log.md` 已追加真实执行记录。
- `Pending_Tasks.md` 已移除完成项并记录遗留问题。
- `AI_Handoff.md` 已反映可供下一位 AI 直接接手的状态。
- Git 变更范围清楚，不包含无关文件。

## Git 规则

- 每完成一个可运行的小步再提交，不把多个无关系统混入同一提交。
- 提交前检查 `git diff` 和 Godot 运行结果。
- 推荐提交前缀：`feat`、`fix`、`refactor`、`docs`、`chore`、`test`。
- 不提交 Godot 生成的 `.godot/` 目录。
- 不覆盖或删除无法确认来源的工作区修改。
- 重要里程碑保留可回退提交。
- AI 不得在没有项目负责人明确要求时擅自提交、推送、清理或重置工作区。

## 两人协作规则

- 主开发者负责脚本、场景、项目设置和资源整合。
- 美术队友优先交付源素材或约定后的导出素材，不直接修改核心场景。
- 导入路径与命名先约定再批量交付。
- 需要美术队友修改 Godot 资源时，按独立分支 / 独立文件分配，避免同时修改同一 `.tscn` 或 `.tres`。
- 占位素材与正式素材保持相同职责和大致尺寸，降低替换成本。

## 多 AI 协作规则

- 聊天记录不是可靠存储。代码文件和 `AI_Context/` 才是 GPT Codex、DeepSeek Codex 及未来 AI 之间的共享事实来源。
- 没有写入 `AI_Context/` 的玩法或技术结论，不视为正式确认设计；AI 不得仅凭模糊聊天记忆实施。
- GPT Codex 默认负责架构、核心系统、复杂问题、整体方向和长期文档一致性。
- DeepSeek Codex 默认负责已明确方案下的小型功能、数值、UI、Prototype 快速验证和简单 Bug 修复。
- 角色分工不改变项目负责人的最终决定权，也不授权任何 AI 擅自扩大范围。
- 不同 AI 修改前必须检查 Git 状态、现有代码与最近工作日志；不得默认另一位 AI 的代码错误，更不得直接删除、回滚或覆盖来源不明的实现。
- 出现冲突时依次参考 `Design_Pillars.md`、`Decision_Log.md`、`Current_Status.md`；仍无法判断则写入待决事项并等待项目负责人确认。
- 完整切换流程见 `AI_Collaboration_Guide.md`。

## 文档同步规则

以下情况必须更新 `Current_Status.md`：

- 功能开始、完成、暂停或被删除。
- 当前里程碑、阻塞项或下一步改变。
- 工程结构或运行方式改变。

以下情况必须更新 `Decision_Log.md`：

- 玩法规则、范围或技术路线被确定或推翻。
- 选择一种方案并放弃了有意义的替代方案。
- 新增会影响后续多个系统的约定。

任何 AI 完成实际开发或重要文档整理后，还必须：

- 向 `AI_Work_Log.md` 追加实际完成内容、修改文件、影响、测试和遗留问题。
- 在 `Pending_Tasks.md` 中移除已完成项，补充新发现的 Bug、待测项和未决设计。
- 更新 `AI_Handoff.md`，使不了解聊天记录的下一位 AI 能直接接手。
- 在重大阶段转换或模型切换前，再次确认 `AI_Handoff.md` 与工作区事实一致。

日志记录结论和理由，不记录冗长聊天过程。
