# AI Collaboration Guide

> 最后更新：2026-07-21  
> 用途：定义 GPT Codex、DeepSeek Codex 及未来其他 AI 在无法共享聊天记录时的项目切换、开发、记录和冲突处理流程。

## 一、协作角色

### GPT Codex

定位：项目主程、技术负责人、核心设计执行者。

主要负责：

- 整体架构与跨系统兼容；
- 核心玩法、新系统和大型重构；
- 复杂 Bug、数据结构和技术路线；
- 玩法设计落地、阶段规划和 AI Context 一致性。

### DeepSeek Codex

定位：开发辅助工程师、快速迭代助手。

适合负责：

- 已明确方案的小功能；
- 简单代码修复、数值和 UI 调整；
- Prototype 快速验证与可替换表现。

不得自行：

- 改变核心玩法或 `Design_Pillars.md`；
- 设计大型系统、推翻架构或删除已有系统；
- 把未决设计变成代码；
- 扩大当前任务范围。

角色划分用于降低风险，不改变项目负责人对所有核心决定的最终权力。

## 二、长期记忆原则

- 聊天记录、模型记忆和口头转述都不是可靠项目存储。
- 代码、场景和版本化的 `AI_Context` 是双方唯一共享事实来源。
- 没有写入 `AI_Context` 的重要设计，不视为正式确认。
- `AI_Work_Log.md` 只记录实际完成活动；`Pending_Tasks.md` 只记录当前状态和真实待办；两者不能互相替代。

## 三、开始开发前

任何 AI 必须按顺序完成：

1. 阅读 `AI_Handoff.md`，确认最近交接、禁止修改项和 Git 风险。
2. 阅读 `Current_Status.md`，确认当前版本、运行状态和已实现系统。
3. 阅读 `Pending_Tasks.md`，确认当前授权内的真实任务、已知问题和未决设计。
4. 阅读 `Design_Pillars.md`、`Decision_Log.md` 和 `Development_Roadmap.md`。
5. 阅读 `AI_Rules.md`、`Development_Rules.md`、`Coding_Standards.md`。
6. 阅读最近的 `AI_Work_Log.md` 记录和与任务相关的 Prototype / 阶段归档。
7. 检查 `git status`、`git diff`、相关代码和场景，识别其他 AI 或用户的未提交修改。
8. 先运行或检查当前基线，再说明本次目标、范围、涉及文件和验收方式。

如果文档和代码不一致，先记录差异；不要默认代码错误，也不要直接回滚另一 AI 的实现。

## 四、任务分配

默认交给 GPT Codex：

- 游戏循环调整、战斗 / 烹饪体系、新数据结构；
- 核心系统、跨系统功能、大型重构；
- 复杂回归、架构冲突与重要设计落地。

可以交给 DeepSeek Codex：

- 已有导出变量的数值调整；
- 明确位置的 UI、文字或简单反馈调整；
- 有清晰验收步骤的小型功能与简单 Bug；
- 不改变设计方向的 Prototype 表现替换。

如果任务从小改动扩展成数据结构或跨系统修改，DeepSeek Codex 应停止、记录当前情况并交回 GPT Codex或项目负责人。

## 五、开发过程中

- 保持任务范围，不顺带实现未来系统。
- 修改前理解现有目的和测试，不默认重写。
- 不删除来源不明的未提交文件。
- 每个阶段保持可运行；发现失败先修复，不在失败基础上继续叠加。
- 未决设计只记录问题，不自行选择答案。
- 发生新阻断、范围变化或协作冲突时，立即同步 `Pending_Tasks.md`。

## 六、开发结束后

完成实际修改后必须：

1. 运行与风险相称的测试和回归。
2. 更新 `Current_Status.md` 的当前事实。
3. 在 `AI_Work_Log.md` 追加一次实际活动记录。
4. 更新 `Pending_Tasks.md`，移除已完成项并记录新问题。
5. 更新 `AI_Handoff.md` 的最近修改、当前重点和下一步。
6. 如果改变玩法、范围、技术路线或长期约定，追加 `Decision_Log.md`；普通代码修复不进入决策日志。
7. 检查 `git status` 和变更范围，明确是否测试、暂存或提交；没有授权不得自行提交。

## 七、模型切换前

当前 AI 必须先完成：

- 保存所有已完成文件，确认不存在半写场景或语法错误；
- 在 `AI_Work_Log.md` 记录已完成、测试和遗留问题；
- 把未完成工作写入 `Pending_Tasks.md`，区分“进行中 / 阻断 / 待讨论”；
- 更新 `AI_Handoff.md`，说明最后安全状态、不要修改内容和精确下一步；
- 记录当前 Git 状态和任何未提交文件；
- 涉及设计变化时更新 `Decision_Log.md`。

完成这些步骤后，才允许另一 AI 在没有聊天记录的情况下接手。

## 八、冲突处理

两个 AI 修改产生冲突时，按以下顺序判断：

1. `Design_Pillars.md`：不可轻易破坏的体验原则。
2. `Decision_Log.md`：正式确认、替代和废弃记录。
3. `Current_Status.md`：当前工程事实。
4. `Pending_Tasks.md`：当前授权和优先级。
5. 代码、场景、测试与最近 `AI_Work_Log.md`：实际实现目的和验证证据。

仍无法判断时：

- 不自行合并两套互斥规则；
- 不删除任一方实现；
- 在 `Pending_Tasks.md` 记录阻断；
- 若冲突会影响未来设计方向，在 `Decision_Log.md` 记录待决策问题；
- 等待项目负责人确认。

## 九、文档职责边界

| 文档 | 负责回答 |
|---|---|
| `Project_Overview.md` | 这是一个什么项目，为什么做，首版范围是什么？ |
| `Design_Pillars.md` | 哪些体验原则不能轻易破坏？ |
| `Decision_Log.md` | 哪些重要决定已经确认、替代或废弃，为什么？ |
| `Current_Status.md` | 当前版本和工程事实是什么？ |
| `Development_Roadmap.md` | 里程碑方向与退出条件是什么？ |
| `AI_Work_Log.md` | AI 实际做过什么、改了什么、测了什么？ |
| `Pending_Tasks.md` | 现在要做什么、有什么问题、什么暂缓？ |
| `AI_Handoff.md` | 没有聊天记录的下一位 AI 如何立即接手？ |

不要把同一大段内容复制到所有文档。状态、历史、待办和决策必须各归其位。
