## Prototype 0.4 状态更新（2026-07-21）

当前里程碑已推进为 **Prototype 0.4：自由准备、通用灶位、牛肉料理分支与多波次测试**。场景进入后立即完成新局初始化并进入 `FREE_PREPARATION`：玩家可自由移动、取材、加工、自动烹饪、摆盘、洗盘、搬锅和放置涮牛肉陷阱，且不会刷怪、没有第一波准备倒计时，也不记录提前营业奖励。界面边缘的“开始营业”只控制敌人来袭，不会重置玩家生命、位置、五格栏、库存、料理、陷阱、灶火、锅具或烹饪进度。失败或第三波完成后的“重新开始”才完整重置新局。

地图现有两个通用灶位与炒锅、煎锅、汤锅三口可移动锅具；三口锅不能同时加热。小炒黄牛肉原路线完整保留。新增战斧牛排的双面自动煎制、局部翻面 QTE、直接近战 / 可选装盘、全局 `has_been_used` 装盘资格、完美大骨头、盐与芥末近战分支；新增每份五片的生牛肉片、汤锅涮煮、涮牛肉五片堆叠与单目标诱食陷阱。攻击与烹饪方式标签已进入物品 / 状态数据，但当前所有敌人倍率均为 1.0，没有实际抗性。

敌人方面新增重型近战味真族：高生命、低移速、较高击退与僵直抗性，以韧性阈值区分普通公牛、战斧和大型公牛的打断能力；毒伤和涮牛肉诱食继续复用既有接口。单波测试扩展为三波：第一波只有普通敌人，第二波混入少量重型，第三波为更密集混合波；波间准备保留生命、库存、快捷栏、锅具、盘子、烹饪和陷阱，可提前开始但只记录秒数、不发放奖励。

验证结果：新增 `prototype_0_4_smoke_test.gd` 9 / 9 组通过；0.1、0.2、0.2.1、0.3、0.3.1、0.3.2 全部回归通过；Godot 4.6.2 资源扫描和主场景无界面启动无 GDScript 解析、断开节点引用或运行时脚本错误。所有新时间、伤害、范围、敌人数、重型参数与三波配置仍是 Prototype 临时值，需要人工试玩。

## Prototype 0.3.2 状态更新（2026-07-20）

该节保留 0.3.2 当时实现记录。其 `WAITING_TO_START` 阻塞界面和“开始游戏后才获得操作权”已在 Prototype 0.4 正式修正为自由准备；0.3.2 的五格栏、生命 HUD、扩大相机、大型暴怒公牛和局部环形提示继续有效。

新增左上角屏幕空间玩家血条，直接监听既有玩家生命数据；快捷栏由三格 Prototype 方案调整为五格，保留真实物品实例、盘子堆叠和满栏保护，并增加数字键 1—5 直选。完美料理的大型暴怒公牛由 6 秒 / 320 速度 / 50 半径 / `152 × 104` 占位体型，调为 24 秒 / 800 速度 / 65 半径 / `198 × 135`，并用分段移动保持高速边界反弹稳定。相机运行时缩放由 `Vector2(1, 1)` 调整为 `Vector2(0.75, 0.75)`，约增加三分之一视野，地图边界不变。

0.3.1 的屏幕固定普通烹饪提示已被本轮替代：全局来袭、波次完成和玩家失败提示继续保留；炒锅改用跟随工位的世界空间环形指示器，以颜色、符号、静态环或阶段进度区分关火、空锅开火、第一阶段、等待辣椒、第二阶段、成菜、焦糊预警、焦糊转焦炭、焦炭和粘锅。料理仍只在明确离散节点改变状态。

验证结果：`prototype_0_3_2_smoke_test.gd` 7/7 组通过；0.1、0.2、0.2.1、0.3、0.3.1 全量回归通过，六个脚本合计覆盖 65 组检查；Godot 4.6.2 编辑器扫描及主场景自然启动无解析、节点引用或运行时错误。五格容量、公牛强化、相机缩放与环形占位表现均为 Prototype 临时方案，仍需人工试玩。

### 结构评估

- 仓库根目录把设计资料、Godot 工程和 AI 上下文分开，边界清楚，适合长期维护。
- `Assets / Audio / Scenes / Scripts / UI` 作为初始化目录足够，不需要在没有实际功能前继续增加空目录。
- 当前按文件类型分组的结构适合早期原型；内容增长后应在现有目录下建立 `player`、`ingredients`、`cooking`、`combat`、`enemies` 等功能子目录，或把强相关场景、脚本和资源放近，避免频繁跨目录查找。
- 当前已有独立的 Prototype 主场景和玩家场景；场景布局只用于灰盒验证，不代表正式关卡。
- 玩法代码按 `core / interaction / items / player / stations / plating / combat / ui / tests` 职责拆分，未把全部规则集中到玩家或主场景脚本。
- `QuickInventory` 独立保存五个 `CarryableItem` 实例和当前格索引；盘子堆叠仍保存真实实例与数量，快捷栏 UI 只负责显示，不拥有物品数据。
- 统一食材柜负责有限库存与安全取出，柜子 UI 负责按钮和输入模态；界面打开时不暂停场景树。
- 炒锅自身保存油、粘锅、离散炒制阶段与锅内物品；炒锅工位只负责放置、加工进度和交互，便于后续替换场景表现。
- 占位视觉由独立组件生成，正式 PNG 或动画替换不需要改变物品数据和料理状态判断。

## 当前风险

- **最大未知是玩法乐趣**：Prototype 0.4 已给出小炒远程、战斧近战和涮肉陷阱三个可操作答案，但尚未通过完整人工试玩证明三者能形成足够有趣的实时构筑；不得因灰盒技术跑通就锁定最终料理架构。
- **“混乱”容易被误做成繁琐**：烹饪步骤必须通过小规模试玩确定。
- **设计状态可能被过早固化**：自由烹饪、调味和牛肉状态路线仍有未决细节，不得用代码替代设计结论。
- **初学成本**：每次只引入当前功能需要的 Godot 知识，避免并行学习过多系统。
- **范围膨胀**：多人混乱合作是长期方向，但可能诱导首版提前开发合作或联机；当前只保留未来可能性，坚持单人验证优先。
- **美术依赖**：玩法原型必须能使用占位素材独立推进。
